# 2026 지난 경기 멘탈지수

관전 기록·로그인 여부와 관계없이 2026 정규시즌과 포스트시즌 경기를 조회한다. **시범경기는 제외한다.** 날짜 추정 대신 공식 시리즈 구분을 사용하며 시범경기 코드 `1`은 수집·저장·조회 대상에서 제외한다. 공식 일정의 정규시즌 그룹은 `0,9,6`, 포스트시즌은 `3,4,5,7`이다. 각 경기는 홈·원정 응원팀 관점의 공통 지수를 제공한다. 개인이 실제로 관전한 구간의 기록이나 개인 시즌 통계와는 별도다.

## 데이터 처리 순서

1. 공식 일정의 경기 ID·시리즈·날짜·참가팀·종료 상태·최종 점수를 저장한다. 점수가 있어도 종료 확인이 없으면 종료 경기로 추정하지 않는다.
2. 종료 경기의 문자중계를 한 번 조회해 이닝·공수·아웃·주자·점수 차와 사건을 정규화한다.
3. 이닝 연속성, 주자 이동, 아웃 수와 최종 득점을 검증한다. 확인할 수 없는 정정이나 사건은 검증 실패로 남긴다.
4. 검증된 전체 사건으로 두 팀 관점의 지수·타임라인을 함께 저장한다.
5. 공개 조회 API와 앱의 `2026 지난 경기 멘탈지수`에서 보여준다.

`ready`는 계산 완료, `incomplete`는 수집했으나 검증 미완료, `missing`은 유효한 계산 결과 없음이다. 미완료 경기의 지수는 null이며 0점이나 부분 계산값으로 대체하지 않는다. 취소 경기 중 공식 경기 ID가 없는 행은 임의 ID를 만들지 않고 수집 메타데이터에 개수만 기록한다.

## 지수 v1

`kbo-mental-v1`은 재미를 위한 휴리스틱이다. 실제 심리 상태, 의학적 스트레스 또는 공식 야구 지표를 의미하지 않는다. 시작값 30에 가중 사건 변화량을 누적하고 표시값을 0~100으로 제한한다. 범위를 넘는 변화량도 내부 합계에 보존한다. 최고 지수와 사건별 변화도 반환한다.

공격팀 기준 기본 변화량:

| 사건 | 변화량 |
|---|---:|
| 아웃 / 삼진 아웃 / 병살 / 삼중살 | +6 / +8 / +18 / +26 |
| 다른 주자 수비 중 낫아웃 출루 | -4 |
| 명시적 진루(무관심·재치·주루방해) | 0 |
| 안타 / 홈런 / 볼넷 / 몸에 맞는 공 | -10 / -20 / -4 / -4 |
| 상대 실책 / 폭투 / 포일 / 보크 | -12 / -6 / -6 / -4 |
| 도루 / 도루 실패 | -4 / +10 |
| 야수선택 / 희생타 | +6 / +2 |

포일·폭투 낫아웃 출루는 해당 원인의 회복 사건으로 계산하고 아웃을 증가시키지 않는다. 다른 주자 수비 중 낫아웃 출루는 별도 `strikeout_reached` 회복 사건이다. 이는 공식 삼진 통계가 아니라 타자의 출루 결과를 반영하는 계산 규칙이다. 삼중살은 명시적 타자·주자 아웃을 합쳐 3아웃이 확인된 경우에만 계산한다.

무관심·재치·주루방해로 명시된 진루는 `runner_advance`로 주자 상황에 반영하되 v1에서는 지수 변화량을 0으로 둔다. 이를 도루나 공식 실책으로 추정하지 않는다.

가중치는 `1 + 주자 수 × 0.15 + (2아웃이면 0.2) + (7회 이후 2점 차 이내면 0.6)`이다. 절댓값을 반올림한 뒤 부호를 적용한다. 수비팀 변화량은 반대 부호다. 결정적 상황을 강조하는 첫 모델이며 승리확률·타구 질·선수 책임을 정밀하게 모델링한 것은 아니다. 선수 이름은 표시용이며 선수 고유 ID·선수별 누적 책임 통계는 아직 제공하지 않는다.

## API

- `GET /v1/seasons/2026/games`: 일정과 수집 범위. `team_id`, `game_date`로 필터링한다.
- `GET /v1/games/{game_id}/mental?team_id=LG`: 참가팀 관점의 계산 결과. 타 팀 요청은 422, 없는 경기는 404다.
- 응답은 모델 버전·계산 시각·원본 해시를 포함한다. 원문 중계는 저장·배포하지 않는다.

일정 정정 시 기존 결과를 무효화하며 두 팀 결과는 한 문서에 원자적으로 저장한다. 같은 최종 점수 안에서 사건 내용만 정정된 경우에는 중계를 다시 수집해야 한다. 운영 자동 정정 감시나 주기 수집은 아직 연결하지 않았다.

## 로컬 검증·재개

서버 디렉터리에서 로컬 MongoDB를 연결하고 실행한다. 아래 URI는 예시이며 운영 비밀값을 저장소에 기록하지 않는다.

```sh
export MONGODB_URI=mongodb://127.0.0.1:27017
export MONGODB_DATABASE=baseball
export ENABLE_KBO_PROBE=true
uv run python -m workers.backfill --schedule-only
uv run python -m workers.backfill --skip-schedule --limit 50
# 검증 미완료 경기를 개선된 파서로 다시 시도
uv run python -m workers.backfill --skip-schedule --retry-incomplete --limit 50 --relay-cache-dir /tmp/baseball-season-relays
# 동일 점수 내 사건 정정을 포함하여 재수집
uv run python -m workers.backfill --skip-schedule --refresh --limit 50
```

기본 요청 간격은 1초이며 최소 0.5초다. `--relay-cache-dir`은 선택한 비공개 임시 디렉터리에만 원문을 캐시해 파서 재검증의 반복 호출을 줄인다. 기본적으로 꺼져 있고 Git 저장소 안의 경로는 거부한다. 캐시는 외부에 공개하지 않으며 필요 없을 때 해당 전용 디렉터리를 삭제한다. `--refresh`는 캐시를 무시하고 원본을 다시 조회·교체한다. 이미 처리된 경기는 기본적으로 건너뛰고 실패 시 저장된 지점부터 재개한다. 기본 50경기 제한은 명시적으로 늘릴 수 있다. 단일 작업자로 실행한다. 파서 변경으로 과거 incomplete를 개선하면 `--retry-incomplete`, 지수 모델 변경 시 버전을 변경하고 재계산한다.

이 수집기는 로컬 기술 검증용이다. 실제 서비스의 데이터 이용 범위·수집 정책을 확인하고 운영 작업과 호스팅을 연결해야 모든 사용자가 원격으로 조회할 수 있다. 로컬 DB 적재는 운영 서버 배포 완료를 의미하지 않는다.

## 일정 확보 범위 · 2026-11-03

1~11월 정규시즌·포스트시즌 22개 월별 조회를 완료했다. 실제 로컬 DB에는 정규시즌 종료 720경기, 종료된 포스트시즌 9경기(와일드카드 1·준플레이오프 3·플레이오프 5), 예정 6경기를 저장했다. 한국시리즈 예정은 종료 경기 수에 포함하지 않는다.

경기 ID 없는 행은 취소 명시 66건과 미확인 8건으로 별도 집계했다. 미확인 8건을 확인한 결과 7건은 점수·리뷰 없이 그라운드 사정이 표시된 과거 일정, 1건은 11월 11일 한국시리즈 7차전 예정이었다. 이들을 완료 경기로 추정하지 않았다. 이동일·휴식일 등 비경기 행은 12건이다. 조회 API의 coverage는 저장된 종료 경기에 대한 계산 현황이며, 원본 전체 일정의 완전성 보증은 아니다.

종료 729경기의 중계 조회를 모두 시도하고 결과를 로컬 DB에 저장했다. 계산 가능한 경기만 `ready`로 제공하며, 원본 누락·불일치·미지원 사건은 `incomplete`로 유지한다. 최신 계산 가능 수는 API의 coverage로 확인한다. 이는 원격 운영 DB 적재·서비스 공개를 의미하지 않는다.

## 최종 로컬 검증 스냅샷 · 2026-11-03

| 항목 | 결과 |
|---|---:|
| 저장된 종료 경기 | 729 |
| 양 팀 지수 검증 완료 | 703 |
| 검증 보류 | 26 |
| 아직 조회하지 않은 종료 경기 | 0 |
| 시범경기 | 0 |
| 검증 완료 경기의 정규화 사건 | 57,529 |

703경기의 두 팀 보고서 1,406건을 저장했다. 양 팀의 사건 ID·변화량, 누적값·타임라인 일치, 점수 범위와 시범경기 제외를 DB 전체로 검사했다. 26경기는 null 점수·빈 타임라인으로 제공한다. [경기별 검증 보류 목록](data/2026-season-audit.json)과 [파서 기준·제한](normalization-evidence.md)을 참고한다.

**모든 지난 경기의 지수를 제공한다는 요구는 아직 26경기에서 미충족이다.** 누락·충돌·정정 근거가 부족한 기록은 독립된 공식 기록으로 대조하거나 검증 가능한 다른 데이터원을 확보해야 한다. 보정이 필요하면 근거·수정 이력과 회귀 테스트를 함께 남겨야 한다. 최종 점수에 맞춰 사건을 만들어 넣지 않는다. 이 수치는 로컬 검증 스냅샷이며 운영 DB나 배포된 앱의 현황이 아니다.
